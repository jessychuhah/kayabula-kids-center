<recommended_technology>
- Framework: Next.js with React and TypeScript.
- Styling: Tailwind CSS and reusable React components.
- Backend: Next.js server actions and/or protected API routes.
- Database: PostgreSQL.
- ORM: Prisma.
- Authentication: Better Auth or Auth.js.
- Validation: Zod and React Hook Form.
- File storage: Cloudinary or AWS S3 with server-side validation.
- Payment provider: A provider approved for Uganda operations, such as Pesapal, supporting MTN Mobile Money, Airtel Money and Visa.
- Hosting: Vercel or a suitable Node.js host with managed PostgreSQL.
- Use environment variables for secrets and never expose provider keys in browser code.
</recommended_technology>

<admin_panel>
- Create a protected route for administrators, for example /admin.
- Require secure authentication and role-based authorization.
- Minimum roles:
  - Admin: full access
  - Editor: manage approved content
  - Viewer: read-only reporting access
- Allow admins to manage:
  - Website content and public sections
  - Programs
  - Impact statistics
  - Images and media
  - Volunteer and partner submissions
  - Contact submissions
  - Donation records and exported reports
  - Public contact and social details
  - Administrator accounts and roles
- Record important admin actions in an audit log.
- Never allow a public user to access admin routes or modify website content directly.
- Protect against CSRF, XSS, SQL injection, unauthorized API access and insecure file uploads.
</admin_panel>

<database_requirements>
- Use PostgreSQL with migrations managed by Prisma or the chosen ORM.
- Store donation records, payment references, payment status, contact submissions, volunteer submissions, partner submissions, website content and audit events.
- Store only information required for operations and payment reconciliation.
- Do not store full card details or CVV numbers.
- Add timestamps and soft-delete or status fields where appropriate.
- Use database indexes for payment references and frequently filtered records.
</database_requirements>

<payment_requirements>
- Use a real, approved payment provider only after verified merchant credentials are supplied.
- Initiate payments on the server and include a unique internal reference.
- Verify successful payments through the provider's signed webhook or server-side verification, not browser redirects alone.
- Reconcile and de-duplicate webhook events.
- Do not display a success state until payment status is confirmed.
- Log payment provider identifiers and status changes without exposing secrets.
- Add refund or payment review states where supported.
- Comply with provider requirements and applicable Ugandan payment regulations.
- Until real merchant credentials and provider approval exist, display payment methods as unavailable and clearly state that checkout is not active.
</payment_requirements>
